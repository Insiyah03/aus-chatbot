# AUS Catalog RAG Assistant: Concepts and Project Pipeline

## 1. Project overview

**Goal:** Build a Retrieval-Augmented Generation (RAG) assistant that
answers questions using the *AUS Undergraduate Catalog 2025--2026* and
grounds answers in retrieved catalog evidence.

The system combines: - **Vector search** for semantic similarity. -
**BM25** for keyword-based retrieval. - **Reciprocal Rank Fusion (RRF)**
to combine retrieval rankings. - **A cross-encoder reranker** to improve
the ordering of candidate chunks. - **An LLM** to generate the final
answer from selected catalog passages.

The key principle is that the LLM should answer from retrieved catalog
content, with accurate PDF page citations, rather than inventing catalog
facts.

------------------------------------------------------------------------

## 2. The full RAG pipeline

It helps to divide the system into two phases: **offline indexing** and
**query-time retrieval and generation**.

### Phase A: Offline document processing and indexing

1.  **Load the PDF**
    -   Load the AUS Undergraduate Catalog PDF.
2.  **Extract text and tables**
    -   Extract the catalog's text and relevant table content.
    -   Preserve the structure needed to interpret course entries,
        prerequisites, policies, and other catalog information.
3.  **Create documents with metadata**
    -   Organize extracted content into document objects.
    -   Attach metadata such as the original PDF page number and section
        information.
    -   Metadata helps with filtering, tracing evidence, and producing
        page citations.
4.  **Split documents into chunks**
    -   Break long documents into smaller passages.
    -   Chunks should be large enough to preserve meaning but small
        enough to retrieve focused evidence.
    -   Keep each chunk linked to its source metadata.
5.  **Generate embeddings**
    -   Use an embedding model to convert each chunk into a dense
        numerical vector.
    -   In the pipeline discussed here, the intended model is
        `mxbai-embed-large`.
    -   Embeddings represent semantic information; they are not simply
        word counts.
6.  **Store vectors in ChromaDB**
    -   Store chunk embeddings along with their text and metadata.
    -   ChromaDB can search for chunks whose vectors are similar to the
        query vector.
7.  **Build the BM25 index**
    -   Tokenize the chunks into searchable terms.
    -   Build an inverted index and calculate/store statistics such as
        term frequencies, document frequencies, and document lengths.
    -   Keep chunk IDs aligned with those used by ChromaDB so results
        from the two retrievers can be matched and deduplicated.

### Phase B: Retrieval and generation at query time

8.  **Receive the user query**
    -   Normalize or tokenize the text as needed by each retrieval
        method.
9.  **Run vector retrieval**
    -   Embed the query using the same compatible embedding model and
        configuration used for the chunks.
    -   Search ChromaDB for semantically similar chunks.
    -   Example configuration discussed earlier: `VECTOR_K = 20`.
10. **Run BM25 retrieval**
    -   Tokenize the query.
    -   Use the BM25 index to find and score chunks that match query
        terms.
    -   Return the highest-scoring chunks.
    -   Example configuration discussed earlier: `BM25_K = 20`.
11. **Combine results with Reciprocal Rank Fusion (RRF)**
    -   Fuse the ranked lists from vector search and BM25 into one
        ranking.
    -   RRF uses the ranks, not the raw vector-similarity and BM25
        scores.
12. **Rerank candidates with a cross-encoder**
    -   Score each candidate using both the original query and the
        candidate chunk text.
    -   Sort candidates by the cross-encoder's relevance scores.
13. **Select the final context**
    -   Take the top-ranked chunks, for example the final top 5.
    -   The number five is a design choice, not a requirement of RAG;
        evaluate whether it provides enough evidence without overloading
        the context.
    -   Preserve the source page metadata.
14. **Generate the answer**
    -   Send the user query and selected chunk text to the LLM.
    -   The LLM produces an answer grounded in the retrieved evidence.
    -   Include accurate catalog page citations.

### Pipeline in one line

**PDF → text/tables → documents + metadata → chunks → embeddings in
ChromaDB + BM25 index → parallel retrieval → RRF → cross-encoder
reranking → final top-k chunks → LLM answer with page citations**

## 3. What is an embedding?

An **embedding** is a dense numerical vector generated by a model to
represent text.

For example, a chunk might be represented conceptually as:

`[0.12, -0.47, 0.08, ...]`

These numbers are learned representations, not counts of individual
words. Vector search compares the query embedding with chunk embeddings
using a similarity or distance measure, such as cosine similarity or
cosine distance, depending on the configuration.

Embeddings are useful when the query and relevant passage use different
wording but express related ideas.

**Example:** A question about "minimum academic requirements" may be
semantically related to a passage discussing "prerequisites," even if
the exact wording differs.

Important: - Embed the chunks when building the vector index. - Embed
each incoming query at query time. - Use the same compatible embedding
model and configuration for both. - BM25 does not require embeddings.

------------------------------------------------------------------------

## 4. What is BM25?

**BM25 (Best Matching 25)** is a statistical, keyword-based information
retrieval algorithm. It gives each candidate chunk a relevance score for
a query and ranks chunks by that score.

BM25 is not an embedding model and does not need dense vectors.

### How the BM25 index is built

Suppose a chunk says:

> CSE 320 requires CSE 220 as a prerequisite.

A simplified tokenizer might produce:

`["cse", "320", "requires", "cse", "220", "as", "a", "prerequisite"]`

A typical BM25 index stores or uses information such as: - Which chunks
contain each term. - How frequently each term occurs in a chunk. - How
many chunks contain each term. - The length of each chunk and the
average chunk length.

The structure mapping terms to the chunks that contain them is called an
**inverted index**.

Conceptually:

  Term             Chunks containing the term
  ---------------- ----------------------------
  `cse`            Chunk 1, Chunk 2
  `320`            Chunk 1, Chunk 2
  `prerequisite`   Chunk 1, Chunk 3
  `calculus`       Chunk 3

The numbers and chunks in this table are illustrative.

### What happens to a query?

For a query such as:

> What are the prerequisites for CSE 320?

BM25 tokenizes the query, looks up its terms in the inverted index,
scores matching candidate chunks, and returns them in descending score
order.

### The three main BM25 factors

1.  **Term frequency (TF):** How often a query term appears in a chunk.
    Repetition helps, but its benefit saturates rather than growing
    indefinitely.
2.  **Inverse document frequency (IDF):** How distinctive a term is
    across the collection. A rare identifier such as a course code can
    be more useful than a common word such as "course."
3.  **Document-length normalization:** Adjusts for chunk length so that
    long chunks are not automatically favored just because they contain
    more words.

A common BM25 formula is:

\[ `\operatorname{BM25}`{=tex}(D,Q)= `\sum`{=tex}\_{t`\in `{=tex}Q}
`\operatorname{IDF}`{=tex}(t) `\frac{f(t,D)(k_1+1)}`{=tex}
{f(t,D)+k_1`\left`{=tex}(1-b+b`\frac{|D|}{\operatorname{avgdl}}`{=tex}`\right`{=tex})}
\]

Where: - (D) is a chunk/document and (Q) is the query. - (f(t,D)) is the
frequency of term (t) in the chunk. - (k_1) controls term-frequency
saturation. - (b) controls document-length normalization. - (\|D\|) is
the chunk length and (`\operatorname{avgdl}`{=tex}) is average chunk
length.

The exact scoring formula and tokenization details can vary between
implementations.

### Is BM25 building a vector of words?

Not in the usual BM25 implementation. It typically builds an inverted
index and uses term statistics.

Do not confuse these three representations:

-   **BM25 inverted index:** term-to-chunk lookup structure plus
    statistics.
-   **Bag-of-words / TF-IDF vector:** numerical features based on
    vocabulary terms.
-   **Embedding vector:** dense, model-generated numerical
    representation of text.

BM25 is especially useful for exact terms, course codes, and technical
vocabulary. It may struggle with synonyms or paraphrases that do not
share words with the query.

A BM25 score is a query-dependent relevance score, not a probability of
correctness. Scores are usually most useful for ranking chunks for the
same query, rather than comparing scores across unrelated queries.

## 5. What is Reciprocal Rank Fusion (RRF)?

**Reciprocal Rank Fusion combines multiple ranked lists into one
ranking.** In this project, it combines the vector-search results and
the BM25 results.

The retrievers have different strengths: - Vector search can find
semantically related passages. - BM25 can find exact terms and
identifiers.

Their raw scores are on different scales, so simply adding the raw
scores is not necessarily appropriate. RRF instead uses each chunk's
rank in each result list.

### Formula

RRF score = sum over retrieval lists of 1 / (k + rank of the chunk)  

Where: - (d) is a chunk. - (R) is the set of retrieval result lists. -
(`\operatorname{rank}`{=tex}\_r(d)) is the chunk's rank in list (r),
starting at 1. - (k) is a constant, commonly 60.

A chunk receives a contribution from each list in which it appears. A
chunk ranked highly by both retrievers can receive a strong combined
score.

### Small example

Suppose `Chunk A` is rank 1 in vector search and rank 2 in BM25, with
(k=60):

\[
`\operatorname{RRF}`{=tex}(A)=`\frac{1}{61}`{=tex}+`\frac{1}{62}`{=tex}
`\approx 0.03252`{=tex} \]

If `Chunk B` appears only at rank 2 in vector search:

\[ `\operatorname{RRF}`{=tex}(B)=`\frac{1}{62}`{=tex}
`\approx 0.01613`{=tex} \]

Chunk A receives the larger fused score because it ranks highly in both
lists.

### What RRF does and does not do

-   **Does:** Combine rankings from different retrievers.
-   **Does:** Reward chunks that appear high in multiple lists.
-   **Does not:** Generate an answer.
-   **Does not:** Read and deeply understand the text like a
    cross-encoder.
-   **Does not:** Guarantee the retrieved chunks are correct.

Configuration discussed earlier: `RRF_K = 60`.

## 6. What is a cross-encoder reranker?

A **cross-encoder reranker** is a neural model that receives the query
and one candidate chunk together and produces a relevance score for that
pair.

For example:

**Query:** "What are the prerequisites for CSE 320?"

**Candidate chunk:** "Students must complete CSE 220 and MTH 201 before
enrolling in CSE 320."

The model processes the query and chunk jointly, using interactions
between their words and context to estimate how relevant the passage is
to the question.

It then scores each candidate, and the application sorts the candidates
by those scores.

### Why use it after retrieval?

Initial retrieval needs to search a potentially large collection
efficiently. A cross-encoder is more computationally expensive because
it must evaluate each query-chunk pair.

A common design is: 1. Retrieve a manageable set of candidates with BM25
and vector search. 2. Fuse the rankings with RRF. 3. Use the
cross-encoder to rerank those candidates. 4. Send only the best final
chunks to the LLM.

The reranker cannot normally recover a relevant chunk that the retrieval
stage never returned.

### Bi-encoder versus cross-encoder

  -----------------------------------------------------------------------
  Bi-encoder / embedding retrieval    Cross-encoder reranking
  ----------------------------------- -----------------------------------
  Encodes query and chunk separately  Processes query and chunk together

  Chunk embeddings can be computed in Scores each candidate for the
  advance                             current query

  Efficient for searching a large     More expensive per candidate
  collection                          

  Retrieves potential matches         Refines the ordering of retrieved
                                      candidates
  -----------------------------------------------------------------------

The cross-encoder score is a relevance signal, not necessarily a
probability or a guarantee of factual correctness.

Reranker discussed for this project: `BAAI/bge-reranker-base`.

## 7. How the retrieval components work together

  -----------------------------------------------------------------------
  Component               Main job                Output
  ----------------------- ----------------------- -----------------------

                          similar chunks          vector scores/distances

  BM25                    Find chunks with        Ranked chunks with BM25
                          statistically relevant  scores
                          matching terms          

  RRF                     Fuse the two rankings   One combined ranking

  Cross-encoder           Evaluate query-chunk    Reranked candidates
                          relevance more directly 

  Top-k selection         Limit the evidence      Final selected chunks
                          passed onward           

  LLM                     Generate a response     User-facing answer
                          using the evidence      
  -----------------------------------------------------------------------

### Why not use just one retriever?

-   Vector search can find related meanings even when wording differs.
-   BM25 can be especially strong for exact course codes and specific
    terminology.
-   RRF combines their complementary rankings.
-   The cross-encoder can improve the order of the combined candidates.

No stage guarantees that the evidence is correct, so retrieval quality
and grounded answer behavior should be evaluated.

## 9. Recommended evaluation

Use a small set of realistic catalog questions with known relevant
source chunks. Include: - Exact course-code questions. - Prerequisite
questions. - Policy questions. - Questions that use synonyms or
paraphrases. - Questions where the answer spans more than one passage. -
Questions whose answers are not present in the catalog.

Useful retrieval metrics:

-   **Recall@k:** Does the top-k retrieved set contain the relevant
    evidence?
-   **MRR (Mean Reciprocal Rank):** How highly is the first relevant
    result ranked?
-   **nDCG (Normalized Discounted Cumulative Gain):** How well are
    relevant results ordered, accounting for graded relevance?

Compare retrieval before and after RRF and reranking. Also check the
correctness of the final answer and page citations. Better ranking is
useful only if it helps the system provide better-supported answers.

## 10. Quick memory recap

Remember the pipeline by asking what each stage does:

-   **PDF processing:** Where does the source content come from?
-   **Documents and metadata:** What is the text, and where did it come
    from?
-   **Chunking:** How do we split the text into retrievable passages?
-   **Embeddings:** How do we represent semantic meaning numerically?
-   **ChromaDB:** How do we retrieve semantically similar passages?
-   **BM25:** How do we retrieve passages using word matching and corpus
    statistics?
-   **RRF:** How do we combine two ranked lists?
-   **Cross-encoder:** Which retrieved passages are most relevant to
    this exact query?
-   **Top-k context:** Which passages should be given to the LLM?
-   **LLM generation:** How do we produce an answer grounded in those
    passages?

**Final one-line summary:**

The AUS RAG assistant processes the catalog into metadata-rich chunks,
indexes them for both semantic and keyword retrieval, combines the
rankings with RRF, reranks candidates with a cross-encoder, and gives
the best evidence to the LLM to generate a catalog-grounded answer with
page citations.
